Chapter Two: Plan and Manage an Azure AI Solution — 25 to 30 Percent
This is the "before you write a line of application code" domain, and it splits into four pieces: choosing the right Foundry services, setting up the solution's infrastructure, managing and monitoring it once it's running, and building in responsible AI from day one. A lot of candidates underrate this domain because it feels less flashy than building an agent. Don't make that mistake. This is architecture judgment, and Microsoft loves testing judgment with scenario questions where two of the four answer choices look almost right, and only one is actually right for the specific constraint described in the question.
Start with choosing services and models. Inside Foundry, you're selecting from large language models, small language models, and multimodal models that reason over text, images, or both. The exam wants you to know when each fits. A small language model is cheaper, faster, and often perfectly adequate for a narrow, well-defined task — classifying which department a support ticket belongs to, or pulling a single field out of a form. A large model earns its extra cost and latency when the task needs broad reasoning, handling open-ended user phrasing, or nuanced judgment calls. A multimodal model comes into play when the input genuinely isn't just text — picture an agent that has to look at a photo of a damaged product and also read the customer's written complaint before deciding how to respond. If a scenario question describes a high-volume, narrow, repetitive classification task and lists a large frontier model as one of the answer options, that's usually a trap: the "correct" architectural answer is often the smaller, cheaper model that's good enough for the job, because part of what's being tested is whether you default to the biggest model out of habit or actually reason about fit and cost.
Beyond picking the model itself, you're choosing services for grounding — meaning, connecting a model's answers to real, current, trustworthy data instead of letting it lean purely on what it memorized during training — and for vector search, the underlying technology that makes semantic retrieval possible in the first place. You're also selecting memory, tool, and knowledge integration services specifically for agent workflows: how does this agent remember what the user said three turns ago, and how does it know which external tools it's allowed to reach for?
Next: setting up the solution. This is infrastructure decision-making. Design the underlying architecture for an AI application versus an agent-based one, because those aren't the same problem — an agent-based solution needs orchestration and tool-calling infrastructure that a simple single-turn chat application simply doesn't require. You need to know your deployment options, how to configure model and agent deployments inside a Foundry project, and — this part tends to surprise people coming from a pure data-science background, though it should feel like home turf for you — how to integrate a Foundry project into a CI/CD pipeline. Coming from years of test automation and release engineering, this should land naturally: Azure wants AI solutions treated like any other production software asset. Versioned. Tested before release. Deployed through a pipeline with gates, not hand-run from someone's notebook because it happened to work on their machine.
Then, managing, monitoring, and securing the live system, and this section has real teeth on the exam. On the management side: quotas, scaling limits, rate limits, and cost control, and this needs to be tracked separately for model workloads versus agent workloads, because they're genuinely different beasts. A simple chat completion is one call per user turn. An agent that plans, calls three tools, and reflects on the result before answering might make six or seven model calls for that same single user turn. If a cost or rate-limit question describes an agentic workflow, do the arithmetic in your head — multiply calls per turn, not just turns per user — because that's usually the trap in the wrong answer choices.
On the monitoring side: tracking model performance over time, watching for drift, watching for safety events, and watching grounding quality. Drift means the model's real-world accuracy is quietly degrading as the data it sees in production diverges from what it was evaluated against originally — think of it like a test suite that used to have full coverage slowly going stale as the application changes underneath it without the tests being updated. Grounding quality is really asking one blunt question: is this answer actually supported by the data that was retrieved, or is the model quietly making things up despite having real documents in front of it? You're also expected to monitor the health of the data pipeline itself: ingestion quality, whether the search index is healthy, and whether retrieval results are actually relevant to the queries being run against them.
On the security side, know four things cold, because they show up constantly as answer choices. Managed identity lets an Azure resource authenticate to another Azure resource without a secret sitting in a config file or a connection string anywhere. Private networking keeps traffic off the public internet entirely, routing it through Azure's private backbone instead. Keyless credentials are the broader modern pattern that managed identity is one specific implementation of — the general shift away from long-lived API keys toward short-lived, automatically rotated, identity-based authentication. And role-based access policies control precisely who, and critically, what — meaning which service principal or managed identity — can perform which specific operations. If an exam question describes a design with an API key hardcoded somewhere, or a shared secret passed around between services, the answer is almost always replace it with managed identity. That pattern repeats often enough that it's worth memorizing as a reflex.
The fourth piece of this domain is responsible AI, and on this exam it is not a soft, values-statement kind of topic — it's fully operational and testable. You need to know how to govern agent behavior through oversight modes and constraints: does a given agent require a human to explicitly approve an action before it executes, or is it allowed to act autonomously within pre-defined limits? You need to configure safety filters, guardrails, and content moderation that catch harmful, off-policy, or simply unwanted outputs before they ever reach a user. You need instrumentation: evaluators and safety evaluations that automatically score a model's or agent's outputs against defined criteria, plus explanation tooling that helps a human actually understand why a model produced a given answer, rather than just seeing the output in isolation. And you need auditing: trace logging that records what an agent did and why, provenance metadata tracking where a given piece of information originally came from, and approval workflows for anything sensitive enough to require a human checkpoint before it goes live. If you remember one sentence from this whole chapter, make it this one: on AI-103, "responsible AI" means specific, configurable, auditable controls you can point to in an architecture diagram — not a philosophy paragraph in a design document that nobody enforces.
Let's slow down on the difference between quotas, rate limits, and token limits, because the exam likes to blur these together in wrong answers, and they're not the same lever. A quota is the total capacity you've been allocated for a resource, typically measured over a longer window — think of it as your overall budget for a given deployment. A rate limit governs how many requests you can send in a short window, like requests per minute, protecting the service from being overwhelmed regardless of your total quota. A token limit is different again — it's the maximum size of a single request or response, measured in the units a language model actually processes text in, and it caps how much content you can stuff into one call regardless of how much quota or rate-limit headroom you have left. If a scenario question describes an application that occasionally fails on very long documents but otherwise runs fine, that's a token-limit problem, not a quota or rate-limit problem, and the fix is chunking the input, not requesting more capacity.
Let's also walk through a cost scenario, because "select the more cost-effective option" is a recurring question shape. Imagine a helpdesk agent that handles roughly ten thousand routine password-reset requests a day, plus a much smaller number of genuinely complex escalations. Running every single request through a large frontier model is the expensive, lazy design. The stronger architecture routes the routine, high-volume, low-complexity requests to a small language model — fast and cheap — and reserves the large model specifically for requests that get flagged as complex or ambiguous, whether by a simple rule or by a lightweight classification step upfront. That's the same instinct as not writing one giant, slow, all-purpose integration test when ten small, fast unit tests would catch the same bugs sooner and cheaper. On the cost-management side specifically, know that Foundry supports both pay-as-you-go consumption and provisioned throughput, where you reserve dedicated capacity in advance for predictable, high-volume workloads — provisioned throughput usually wins on cost at high, steady volume, while pay-as-you-go wins for spiky or unpredictable traffic. Budgets and cost alerts sit on top of either model, and configuring them is part of what "managing" a solution means on this exam, not just an afterthought you set up once and forget.
One more scenario, this time on the networking and security side. A financial services company is building an AI solution that must never let data leave their private network, even briefly, and must satisfy strict regulatory auditing. Two architecture options are on the table: a public endpoint locked down with API-key authentication and IP allowlisting, or a private endpoint with managed identity and full network isolation. On this exam, in a regulated, security-sensitive scenario like that, the private endpoint with managed identity is almost always the intended answer, even though the public-endpoint-plus-allowlist option might work perfectly well in practice for a less regulated business. The exam is testing whether you reach for the strongest available control when the scenario explicitly signals a high-compliance environment, not just whether the design technically functions.
Let's do one more quick scenario before moving on, the way an exam question might frame it. Imagine a company wants an agent that can issue refunds automatically for orders under fifty dollars, but anything above that threshold needs a person to sign off first. Where does that split actually live, architecturally? It's not a content filter, and it's not a monitoring dashboard — it's an approval workflow tied to an oversight mode, gating the agent's tool-calling permission based on a business rule. That's the kind of precise mapping between a business requirement and the specific Foundry concept that answers it, which the real exam rewards.
Quick recap before we move on. Domain one is architecture and governance: pick the right model and service for the actual job rather than reflexively reaching for the biggest model, design infrastructure that treats AI like production software with CI/CD behind it, keep a close eye on cost, drift, and grounding once it's live, secure everything with managed identity and private networking rather than static secrets, and bake safety and auditability into the design from the start rather than bolting it on after something goes wrong.
Chapter Three: Implement Generative AI and Agentic Solutions — 30 to 35 Percent
Here's the big one. Nearly a third of your score, and it's genuinely the conceptual center of the whole exam — the domain that the vision, text, and extraction domains all ultimately feed into. It breaks into three parts: building generative applications, building agents, and optimizing and operationalizing what you've built.
Building generative applications first. At the foundation, you need to deploy and consume different model types through Foundry — large models, small models, code-focused models, and multimodal models — and pick correctly between them for a given scenario, echoing domain one but now at the implementation level rather than the planning level. The single most important pattern in this entire exam is retrieval-augmented generation, universally shortened to RAG. If you're not completely solid on RAG, stop this recording, go review it properly, and come back — because it threads through domains two, four, and five, and a surprising number of questions in unrelated-sounding domains are secretly testing whether you understand RAG.
Here's the pattern, stated plainly. Instead of asking a language model to answer purely from what it memorized during training, you first retrieve relevant, current, trustworthy documents or data — almost always through a search index — and then hand both the user's question and those retrieved documents to the model, instructing it to answer using that grounded material rather than its own memory. This solves two problems simultaneously. First, it lets a model answer questions about information it never saw during training — your company's internal wiki, last week's product changes, a customer's specific order history. Second, and just as important, it dramatically reduces the model inventing facts, because the answer is now tethered to real retrieved text instead of pure, unverifiable memory. Think of RAG as giving an open-book exam instead of a closed-book one — the model is still doing the reasoning, but it's reasoning over evidence you handed it, not guessing from what it half-remembers.
Past RAG, this section covers designing workflows — tool-augmented flows and multistep reasoning pipelines, where a model doesn't just answer in one shot but plans out a sequence of steps, possibly calling tools or other models along the way before producing a final answer. It covers evaluating models and applications specifically for fabrications — invented, unsupported claims — as well as for relevance, quality, and safety, using both automated evaluators and structured human review. And it covers integrating all of this through Foundry SDKs and connectors, plus configuring how your application code actually connects to a Foundry project in the first place. Think of that last part as the plumbing that ties your application to the AI backend — unglamorous, but it's exactly the kind of thing a "which configuration is missing" question likes to probe.
Now, building agents — the part of this exam that genuinely didn't exist in this form on the older exam. First, you define the agent itself: its role, its goals, how it tracks a conversation over time, and the schema for the tools it's allowed to call. That last part matters more than it sounds like it should. A tool schema is essentially a contract that tells the model exactly what a tool does, what inputs it expects, and what it returns, so the model can decide correctly when and how to invoke it, and just as importantly, when not to. This is conceptually identical to how Model Context Protocol tools get described to Claude, if that's a reference point that's already comfortable for you — same underlying idea, different vendor's name for it.
Then you build agents that combine retrieval, function-calling, and conversation memory — an agent that can look things up, take real actions through defined functions, and remember what's already been discussed earlier in the conversation so it doesn't ask the user to repeat themselves. You integrate the specific tools an agent needs: APIs, knowledge stores, search, content understanding services, and custom functions you write yourself for the specific business problem.
From there, the exam pushes into multi-agent territory: implementing orchestrated multi-agent solutions, where more than one specialized agent collaborates on a single task. Picture a research assistant scenario — one agent plans out what needs to be researched and in what order, a second agent actually retrieves information from various sources, and a third agent synthesizes everything into a final written response, all coordinated by an orchestrator that decides which agent acts next and passes information between them. You need to know how to build autonomous or semi-autonomous workflows, and — tying straight back to domain one — how to wrap them in safeguards and approval controls, because an agent that can take real-world consequential actions, like sending an email, modifying a customer record, or spending money, needs hard limits on what it's allowed to do without a human checking in first. Finally, integrating monitoring specifically built for agents, and knowing how to do error analysis when an agent's behavior goes sideways: did a particular step in the chain fail, was it a bad tool call with malformed arguments, a hallucinated fact that slipped through, or a misread instruction from earlier in the conversation? Being able to localize where in a multi-step agent chain something broke is exactly the kind of diagnostic thinking your testing background already trains for — you're used to tracing a failure back to the specific step that caused it rather than just noting "the test failed."
The third piece is optimizing and operationalizing. This covers prompt engineering and tuning model parameters — things like temperature, which controls how creative and varied versus deterministic and repeatable a model's output is going to be. It covers techniques like model reflection and chain-of-thought evaluation, where a model, or a separate supervising process, checks its own reasoning or draft output before finalizing an answer, sometimes called self-critique — essentially building a review step into the pipeline itself rather than trusting the first output blindly. And it covers observability at the systems level: tracing requests end to end through a multi-step agent flow, tracking token usage and cost per request, watching safety signals fire in real time, and breaking down latency to find exactly where time is actually being spent — was it the model call, the tool call, or the retrieval step that was slow? Finally, orchestrating multiple models and flows together, sometimes deliberately blending large language models with traditional, deterministic rules engines, because not every decision in a real system should be handed to a model. Sometimes a plain if-then rule is more reliable, cheaper, faster, and far more auditable than an LLM call, and knowing when to not reach for a model is part of what separates a solid architect from someone who treats every problem as a prompting problem.
Let's pause on a question that trips people up constantly: when do you fine-tune a model instead of, or in addition to, using RAG? These get confused because both feel like "teaching the model something," but they solve genuinely different problems. Fine-tuning adjusts the model's underlying weights based on examples you provide, and it's the right tool when you need the model to consistently follow a specific style, tone, or output format — say, always responding in your company's exact voice, or always producing a very particular structured format — or when you need it to reliably perform a narrow task pattern it doesn't do well out of the box. What fine-tuning is bad at is keeping the model current: the knowledge baked in during fine-tuning goes stale the moment your underlying data changes, and re-fine-tuning for every data update is slow and expensive. RAG solves the opposite problem — it keeps the model grounded in fresh, current, easily updatable information, without touching the model's weights at all, but it doesn't reliably change how the model writes or behaves stylistically. In practice, plenty of production systems use both together: a fine-tuned model for consistent behavior and format, fed by a RAG pipeline for current facts. If an exam question describes a need for "always up to date" information, that's RAG. If it describes a need for "always follows this exact format or tone," that's fine-tuning. If it describes both, the answer is both.
Now let's get concrete about orchestration patterns for multi-agent systems, because "orchestrated multi-agent solutions" is a phrase on the outline that covers more than one actual shape. A sequential pattern chains agents in a fixed pipeline — agent A always finishes before agent B starts, like a linear pipeline where each stage depends on the previous one's output. A supervisor, or router, pattern uses one coordinating agent that looks at an incoming request and decides which specialist agent should handle it, sometimes routing to different specialists for different sub-parts of the same request — this is the pattern behind that research-assistant example from a moment ago, where a planning agent decides who does what. A parallel, fan-out-and-fan-in pattern sends the same request to multiple agents simultaneously and then combines their results — useful when you want several independent perspectives or several independent pieces of information gathered at the same time rather than one after another, trading a bit of extra cost for lower total latency. Knowing which shape a scenario is describing, and picking the term that matches it, is a recurring exam skill in its own right.
Worth going one level deeper on function calling too, since it's the mechanism that actually makes tool-using agents work. When an agent decides to call a tool, the model doesn't execute anything itself — it produces a structured request, matching the tool's schema, that your application code then actually executes, capturing the real result and handing it back to the model to continue reasoning with. That means error handling lives in your application code, not inside the model: if a tool call fails, returns malformed data, or times out, your system needs a defined behavior — retry, ask the model to try a different approach, or escalate to a human — rather than just letting the agent silently continue as if nothing went wrong. This is exactly the kind of failure-mode thinking test automation trains you for: a tool call is functionally a flaky external dependency, and a well-designed agent needs the same kind of defensive handling around it that you'd build around any unreliable API call in a test framework.
One more worked example to tie generative and agentic solutions together end to end. Picture an order-fulfillment agent that needs to check inventory, calculate shipping cost, and send a confirmation email, all triggered by one customer message. A supervisor agent receives the request, recognizes it needs three distinct capabilities, and calls three tools in sequence — an inventory-lookup function, a shipping-calculation function, and an email-sending function — with each tool's schema clearly defining its expected inputs and outputs. If the inventory check comes back showing the item is out of stock, the orchestration logic needs to branch: skip shipping calculation entirely, and instead trigger a different response path that tells the customer and perhaps checks a restock date. That branching logic, built on top of tool results rather than hardcoded in advance, is what separates a genuinely agentic workflow from a simple fixed script, and it's exactly the kind of scenario the exam likes to describe and then ask "what happens next" or "what's missing from this design."
Let's run one more scenario. Say a multi-agent customer-support system starts giving inconsistent answers to the same question asked twice in a row. Where do you look first? Not the model choice, and not the prompt wording — you trace the request through observability, following it step by step through the orchestrator to find exactly which agent, which tool call, or which retrieval step introduced the inconsistency, the same way you'd bisect a flaky test failure back to its root cause rather than just re-running it and hoping.
If you want a one-line summary of domain two: build a generative pipeline that's grounded in real data through RAG, wrap that pipeline in an agent that can plan, remember, and call tools safely, coordinate multiple agents together when the task genuinely calls for it, and instrument the whole system so you can see exactly what it's doing and diagnose it precisely when it misbehaves.
Chapter Four: Implement Computer Vision Solutions — 10 to 15 Percent
Ten to fifteen percent of the exam, and it splits cleanly into three areas: generating visual content, understanding visual content, and applying responsible AI specifically to that visual content.
Generation first. This covers producing images and video from text prompts, or from a combination of text and reference media — think "generate an image of X," or "create a short video based on this written description plus this reference clip I'm providing." Within that, you need editing workflows: inpainting, which means regenerating just a masked portion of an existing image while leaving everything outside that mask untouched; mask-based edits more generally; and prompt-driven modifications, where you describe a desired change in plain words instead of manually editing pixels yourself. The same underlying idea extends to video editing workflows, and you're expected to know how to select and apply the right generation or editing control for a given creative or business requirement — knowing, for instance, when a full regeneration is appropriate versus when a targeted, masked edit preserves more of the original asset.
Understanding is the flip side of generation — instead of creating visual content, you're extracting meaning from content that already exists. This covers analyzing visual context using multimodal models, and configuring captions, both concise one-line captions and more detailed, extended descriptions, for either a single image or a batch of images at once. It covers visual question answering, where a system answers a specific question grounded in what's actually depicted in an image, rather than producing a generic guess disconnected from the actual pixels. There's a genuinely practical, real-world angle here too: generating alt text and extended descriptions that meet accessibility guidelines. That's a production requirement plenty of teams have to satisfy for compliance and inclusivity reasons, not a throwaway exam topic. You'll also see Azure AI Content Understanding show up specifically for extracting visual characteristics from images, running video analysis workflows end to end, and choosing between single-task pipelines — fast, narrow extraction of one specific thing — versus what's called pro-mode, a deeper, more thorough extraction pipeline for when a quick single-pass answer genuinely isn't enough. And you need to know how to identify specific objects, components, and regions within an image or a video — classic object-detection and localization territory.
Then, responsible AI for multimodal content specifically. This means classifying content as unsafe or disallowed when it's visual rather than text-based — the same safety mindset from domain one, now applied specifically to images and video rather than to written language. It also covers a subtler and genuinely interesting threat: detecting and mitigating indirect prompt injection carried through embedded text inside an image. Picture a picture that contains hidden instructions — text baked into the image itself — deliberately designed to hijack a model's behavior when a vision-capable model reads and processes that image. That's a real, documented attack pattern, and the exam expects you to know it exists and how to guard against it. Finally, enforcing visual policy rules: watermark detection, prohibited symbols, brand compliance requirements, and automatically flagging inappropriate content before it reaches a user or gets published somewhere.
A little more vocabulary worth locking in on the understanding side, because the exam uses these terms precisely and expects you to as well. Image classification answers "what is this image, overall" — a single label for the whole picture. Object detection goes further, answering "what's in this image, and roughly where" — drawing boxes around individual items. Segmentation is more precise still, identifying the exact pixel boundaries of an object rather than just a rough bounding box. If a question describes needing to count how many defective parts appear on a manufacturing line image and roughly where they are, that's object detection. If it describes needing the exact outline of a defect for a robotic arm to act on, that's segmentation. Getting these three terms mixed up is an easy way to pick a plausible-sounding wrong answer.
On generation controls specifically, know that consistency matters as much as raw quality in production use — if a brand needs the same character or product to look visually consistent across a whole series of generated images, that's typically handled through reference-image conditioning and, in some tools, deterministic seed values that let you reproduce a very similar result on demand rather than getting a completely different image every time from the same prompt. And built-in content filtering applies at generation time too, not just after the fact — meaning a well-designed pipeline blocks disallowed image generation requests before an image is ever produced, rather than generating something problematic and only catching it afterward with a separate moderation pass.
Here's a scenario that ties several pieces of this domain together. An e-commerce company wants AI-generated alt text for a catalog of eighty thousand product images, to meet accessibility requirements. The naive design just runs every image through a captioning model and publishes the output directly. The stronger design recognizes two things the exam wants you to catch: first, this is a multimodal understanding task, specifically extended-description generation tuned for accessibility guidelines rather than generic captioning; and second, given the scale and the compliance stakes involved, it should route a sample of outputs through human review rather than publishing everything fully automated and unchecked — the same oversight-mode thinking from domain one, applied here to a vision workflow instead of an agent taking business actions.
Quick recap: vision on this exam is generate, understand, and govern. Create images and video on request, extract meaning and accessible descriptions from existing visual content, and apply safety controls that specifically account for the fact that a picture can carry hidden risk — like embedded instructions — that plain text simply can't.
Chapter Five: Implement Text Analysis Solutions — 10 to 15 Percent
Also ten to fifteen percent, and it covers two related but genuinely distinct areas: applying language models to analyze text, and implementing speech solutions.
On the text analysis side, this is where a lot of what used to be handled by dedicated, narrow "Cognitive Services Language" endpoints now gets framed through generative prompting and Foundry Tools instead of only through single-purpose services. You need to know how to extract entities, topics, and summaries from text, and how to produce structured JSON output from unstructured input — this last point matters a great deal in real systems, because an agent or a downstream application usually needs a predictable, machine-parseable format, not loose free-form prose it then has to somehow interpret. You need to detect sentiment and tone, and also flag safety issues or sensitive content within text — is this message hostile, is it disclosing something it shouldn't, does it need to be escalated. You need to translate text, either through Azure Translator exposed as a Foundry Tool, or through an LLM-powered translation flow, and know roughly when each approach fits better. Dedicated translation services tend to be faster, cheaper, and more consistent for straightforward language pairs and general text. LLM-powered flows tend to be worth the extra cost when translation needs to preserve domain-specific tone, technical terminology, or context that a purpose-built translator would flatten. And you need to customize outputs for specific domain tasks — summarizing for a compliance review has different requirements than summarizing the same document for a customer-facing FAQ, even though both start from the identical instruction "summarize this."
Speech is the second half of this domain, and don't discount it just because it can feel like the smaller topic — it's fully in scope and worth real study time. Speech-to-text and text-to-speech conversion, specifically framed around agentic interactions, meaning a voice interface where a user talks to an agent out loud and the agent talks back, rather than a purely text-based chat window. Integrating speech as one modality an agent can use among several, including custom speech models trained for a specific vocabulary, accent, or industry jargon that a generic speech model would mishear. Enabling multimodal reasoning directly from audio input, where a model reasons about what's actually present in an audio clip — tone, background sound, who's speaking — not just a flattened transcript stripped of all of that context. And translating speech directly into other languages using language models combined with Foundry Tools, rather than requiring a separate transcribe-then-translate-then-synthesize pipeline built by hand.
Let's dig a little deeper into structured JSON output, because it's an easy point to lose if you underrate it. When a downstream system — an agent, a database, another service — needs to consume a model's output programmatically, free-form prose is close to useless no matter how accurate it is, because there's nothing reliable to parse. The fix is instructing the model to produce output matching a defined schema, and validating that output against that schema before anything downstream trusts it. A common exam trap is a scenario that clearly needs machine-readable output feeding directly into another automated system, with one answer choice offering a nicely worded natural-language summary and another offering structured JSON extraction — the natural-language option can look attractive because it reads better to a person, but it's the wrong architectural choice the moment a machine, not a human, is the actual consumer of that output.
Let's also walk through a realistic speech scenario, because it pulls together several strands from this chapter at once. A multilingual customer-support voice bot needs to take a spoken question in one language, understand it, reason about the right answer, and respond out loud, potentially in a different language than the one the customer used. That's genuinely several steps chained together: speech-to-text to get a transcript, translation if needed, an LLM reasoning step — possibly grounded through RAG if the answer depends on account-specific data — and finally text-to-speech to convert the response back into audio, potentially in yet another target language. Each step in that chain adds latency, and a design that naively runs every step sequentially and waits for each one to fully finish before starting the next can end up with an unacceptably slow, awkward pause before the bot responds. A stronger design looks for opportunities to stream partial results — starting text-to-speech on the beginning of a response while the rest is still being generated, for instance — because in a voice interface, perceived responsiveness matters as much as raw accuracy.
One more piece worth naming explicitly: detecting and flagging personally identifiable information, PII, and other sensitive content within text specifically for compliance purposes. This sits alongside general sentiment and safety detection, but it's a distinct capability — recognizing that a piece of text contains a social security number, a medical detail, or a credit card number, so that a system can redact it, refuse to log it in plain form, or route it through a stricter handling path before it's stored or forwarded anywhere.
Recap: text analysis on this exam blends the classic natural language processing tasks — entities, sentiment, translation, summarization — with the newer expectation that a lot of this now happens through generative prompting rather than narrow dedicated endpoints, and it explicitly folds speech in as a first-class agent modality, not an afterthought bolted onto a text-only system.
Chapter Six: Implement Information Extraction Solutions — 10 to 15 Percent
The last domain, again ten to fifteen percent, and it's really about one core problem underneath all the specific service names: turning messy, real-world documents and media into clean, structured, trustworthy data that a retrieval pipeline or an agent can actually use with confidence. It splits into building the retrieval and grounding pipeline, and extracting content from documents specifically.
For the pipeline side: you need to ingest and index a mix of content types — documents, images, audio, and video — into a searchable system that an application or agent can query against. You need to configure semantic search, hybrid search, and vector search specifically for grounding generative answers, and it's worth being precise about the difference between these, because the exam will test that precision directly. Keyword search matches literal words — if the document doesn't contain the exact term you searched for, it won't be found, even if it's obviously relevant in meaning. Vector search matches meaning instead, by comparing numerical representations of text called embeddings, so a query about "canceling a subscription" can successfully match a document that says "how to end your membership," even though not a single word overlaps between the two phrases. Hybrid search combines both approaches together, and it's usually the most robust choice for real production systems, because it catches literal keyword matches for things like product codes or exact names, while also catching semantic matches for paraphrased or loosely worded queries. If an exam question describes a scenario where users search using exact product IDs and natural-language questions in the same system, hybrid search is almost always the correct answer over either pure approach alone.
You also need to know how to implement enrichment — running custom or built-in processing skills over text, images, and document layout to pull out extra structure before anything gets indexed — and how to configure RAG ingestion pipelines that include OCR, optical character recognition, specifically for scanned or image-based documents that don't contain any machine-readable text to begin with. Finally, connecting these retrieval pipelines to downstream workflows and agent tools, so that an agent can actually call into this search index as one of its available tools during a multi-step task, rather than the index existing in isolation from everything you built in domain two.
For document content extraction specifically: multimodal extraction pipelines that combine OCR, layout analysis — meaning genuinely understanding a document's structure, not just its raw text, so a table gets recognized as a table with rows and columns, and a header gets recognized as a header rather than just another line of undifferentiated text — and targeted field extraction, like reliably pulling a specific invoice number or a total dollar amount out of a form regardless of exactly where it happens to sit on the page. You need to know how to produce clean, grounded representations of that extracted content, specifically formatted for agents or RAG pipelines to consume downstream, using Content Understanding. And you need to know how to implement analyzers that generate either structured output or markdown output through Content Understanding, choosing between the two depending on what the downstream system actually needs to consume.
Let's talk about chunking, because it's one of those unglamorous implementation details that quietly determines whether a whole RAG system works well or poorly, and the exam expects you to reason about it, not just name it. Before a document goes into a search index, it typically gets split into smaller chunks, because retrieval works better over focused passages than over one giant document, and because a model's input has limits on how much retrieved text it can usefully absorb at once. Chunk size is a real tradeoff: chunks that are too small lose surrounding context, so a retrieved fragment might not make sense on its own; chunks that are too large dilute relevance, pulling in a lot of irrelevant text alongside the one useful sentence a query actually needed. A common practical fix is overlapping chunks slightly at the boundaries, so a fact that happens to sit right at a chunk boundary does not get awkwardly split in half and lost. If a scenario describes a RAG system returning technically-matching but oddly incomplete or out-of-context answers, chunking strategy is one of the first places to suspect, right alongside embedding quality and index configuration.
Just as important, and directly tied back to security in domain one: metadata filtering and permission-aware retrieval. A search index for a legal or HR document repository shouldn't just return the most semantically relevant chunk regardless of who's asking — it needs to filter results based on the requesting user's actual permissions, department, or clearance level, sometimes called security trimming. Picture a contracts repository where a hybrid search index lets any employee search across every contract by natural language, but a paralegal should only ever see full contract text for matters they're assigned to, while an executive might have broader access. The retrieval pipeline needs to apply that permission filter before handing results to the generative model, not after, because a model that already has the sensitive text in its context window can't reliably be told after the fact to pretend it never saw it. That's the same throughline connecting domain one's role-based access policies to information extraction's retrieval pipelines: security has to be enforced at the data layer, not patched on afterward at the response layer.
Recap: information extraction is the unglamorous but genuinely essential domain. Get messy documents, images, and audio into a clean, searchable, well-structured form, using the right blend of keyword, vector, and hybrid search for the actual query patterns you expect, so that everything you built in domain two — the RAG pipelines and the agents sitting on top of them — actually has good, trustworthy data underneath it to work with. Garbage in, garbage out applies just as much to an agent as it does to any pipeline you've ever tested.
Chapter Seven: A Spoken Glossary
Before the self-test, here's a fast run-through of the vocabulary that shows up again and again across every domain, said out loud enough times that the terms stop feeling unfamiliar the moment you see them in a question stem.
Azure AI Foundry: the umbrella workspace where you select models, configure tools, deploy agents, and monitor everything once it's running. If a question mentions a "project," it almost always means a Foundry project.
Foundry Tools: the reusable, pluggable capabilities — search, translation, content understanding, and others — that a Foundry project can wire into an application or hand to an agent as a callable tool.
Grounding: connecting a model's output to real, verifiable data, rather than letting it answer purely from what it memorized during training. Grounding quality is a direct measure of how well an answer is actually supported by that real data.
Retrieval-augmented generation, RAG: retrieve relevant data first, then hand it to the model alongside the user's question, so the answer is built on real, current evidence instead of pure memory.
Embeddings: numerical representations of text that capture meaning rather than exact wording, which is what makes vector search possible in the first place.
Vector search: search based on meaning, using embeddings, so differently worded queries can still match the right content.
Hybrid search: keyword search and vector search combined, generally the most robust choice for real-world query patterns that mix exact terms and natural language.
Chunking: splitting documents into smaller pieces before indexing them, because retrieval and model context windows both work better over focused passages than over entire documents at once.
Tool schema: the contract describing exactly what a tool does, what inputs it needs, and what it returns, so a model can decide correctly when and how to call it.
Orchestration: the coordination logic that decides which agent or step acts next in a multi-agent or multistep workflow — sequential, supervisor-routed, or parallel fan-out being the three shapes worth knowing by name.
Oversight mode: the setting that determines whether an agent can act autonomously within limits, or must pause for human approval before taking a given action.
Drift: a model's real-world accuracy quietly degrading over time as production data diverges from what it was originally evaluated against.
Managed identity: a way for an Azure resource to authenticate to another Azure resource without any stored secret or key.
Content Understanding: the Foundry capability specifically for extracting structured meaning — visual characteristics, document layout, fields — from multimodal content like images, video, and documents.
Indirect prompt injection: hidden instructions embedded in content, like text baked into an image, designed to hijack a model's behavior when it processes that content.
Security trimming: filtering search results based on a requesting user's actual permissions before those results ever reach a generative model, rather than trying to filter or redact after the fact.
Hold onto those fifteen terms specifically. A large share of the exam's trickier scenario questions come down to correctly matching a described situation to the right term from this list.

Question one. A team wants to reduce a model's tendency to invent facts when answering questions about internal company documents. What's the primary architectural pattern that addresses this?
 Retrieval-augmented generation, RAG — ground the model's answer in retrieved, real documents rather than letting it rely purely on memorized training data.
Question two. An architecture review finds an API key hardcoded in application configuration to authenticate to an Azure AI service. What should replace it?
 Managed identity — authenticate the resource to the service without a stored, static secret at all.
Question three. A search system needs to handle both exact product-code lookups and loosely worded natural-language questions from the same users. Which search approach fits best?
 Hybrid search — combining keyword matching for exact terms with vector search for semantic, paraphrased queries.
Question four. An agent is going to be allowed to issue small refunds automatically, but larger refunds need a person to sign off first. What's the specific mechanism that implements that split?
 An approval workflow tied to an oversight mode, gating what the agent's tool-calling permissions allow it to execute autonomously versus what requires human sign-off first.
Question five. A model's real-world accuracy is quietly getting worse over time as production data diverges from what it was originally evaluated against. What's this phenomenon called, and what domain covers monitoring for it?
 Drift, and it's covered under managing and monitoring in domain one — the same domain that covers grounding quality and safety event monitoring.
Question six. An image contains hidden text specifically designed to manipulate a vision-capable model's behavior when it processes that image. What's this attack pattern called?
 Indirect prompt injection through embedded content — a threat covered specifically under responsible AI for multimodal content in the computer vision domain.
Question seven. A document processing pipeline needs to recognize that a block of text is actually a table with rows and columns, not just an unstructured paragraph. What capability is being tested here?
 Layout analysis, part of document content extraction in the information extraction domain, distinct from simple OCR, which only reads characters without understanding structure.
Two more, since these two concepts are easy to blur together and worth locking in separately.
Question eight. A team needs a model to consistently respond in a very specific structured format and company tone across thousands of interactions, and that requirement isn't going to change often. Which technique fits better, fine-tuning or RAG?
 Fine-tuning — this is about consistent style and behavior, not about needing fresh, frequently changing information, which is what RAG is for.
Question nine. Retrieved passages coming back from a search index are technically on-topic but keep cutting off mid-thought, leaving the model with incomplete context to answer from. What implementation detail is the most likely culprit?
 Chunking strategy — the chunk size or overlap is probably splitting relevant information across chunk boundaries in a way that loses context.
